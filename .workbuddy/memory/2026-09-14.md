## fix(auction): 自动拍卖跨凌晨 5 点卡在月卡弹窗

- 现象: 任务运行到本地 5 点(月卡刷新)时, 月卡弹窗盖住拍卖界面, 所有 `_is_*_screen` 判定失效, 轮询一直空转到 `ROUND_TIMEOUT=600s` 后失败, 下一轮重复, 表现为永久卡死。
- 根因: `BaseNTETask` 已在 `__init__` 里把月卡检测注册进 `scene_flow.interrupt`, 但只对走 `scene_flow.run()` 的任务生效(经 `safe_point`/`before_step`)。`AutoBidAuctionTask` 不走 flow, 且四处轮询循环从未调用 `check_monthly_card` / `handle_monthly_card`, 与 WhirlwindTask / DSDFarmTask / VolleyballTask / AutoHeistTask 的处理方式不一致。
- 修复: `src/tasks/AutoBidAuctionTask.py` 新增 `_handle_external_interrupts()`(检测到时间窗内的月卡弹窗就调 `handle_monthly_card()`), 并在 4 个轮询循环各插入一次调用: `_stage_match`、`_handle_match_click`、`_wait_bid_outcome`、`_stage_result`。插入位置在 `self.next_frame()` 之后, 保证 `handle_monthly_card` 里的 find_one 用的是新帧。
- `check_monthly_card` 先判时间窗(4:59:30~5:01:30), 窗口外几乎零开销, 不增加常态轮询成本。
- 未覆盖路径(可接受): 出价中间步骤(`_attempt_bid`)被弹窗打断时该轮直接失败重试, 最多多损失约 1 轮。
- 补充(同一 bug 的相邻边界): `check_monthly_card` 只在 5 点前后 2 分钟时间窗内生效, 且时间窗仅由 `NTEOneTimeTask.run()` → `set_check_monthly_card()` 武装(4:59:30~5:01:30, 5:00 之后启动会顺延到第二天), 所以"5 点后才启动任务且弹窗还在"不会被时间窗命中。新增 `_recover_blocking_popup()`(用 `find_monthly_card()` 特征兜底, 异常吞掉只告警), 挂在 `do_run` 的轮次失败分支, 正常路径零额外开销。
- 测试: `tests/TestAutoBidAuctionTask.py` 新增 9 个用例(interrupt handler 命中/窗口外 no-op + 4 个循环各一条集成断言 + 3 条 `_recover_blocking_popup`)。验证命令:
  `.venv/Scripts/python.exe -m unittest tests.TestAutoBidAuctionTask tests.TestAutoBidAuctionFrames tests.TestAuctionHouseUpkeepTask tests.TestNTEOneTimeTask tests.TestSceneFlow` → 71 + 44 tests OK。

## 重构: 改用项目既有的 sleep_check 约定(已提交 `dab1a93`)

项目里处理月卡弹窗有**两种**既有模式, 拍卖任务原本两种都没用:
1. **`sleep_check()` 钩子 + `sleep_check_interval >= 0`** —— WhirlwindTask / DSDFarmTask / VolleyballTask / AutoHeistTask。ok-script 的 `executor.sleep()` 内按 interval 调用, 调用前 `next_frame()`; `in_sleep_check` 标志保证重入安全(所以钩子里再点击/睡眠不会递归)。Whirlwind/DSDFarm 是靠 `BaseCombatTask.__init__` 里的 `sleep_check_interval = 0.1` 生效, Volleyball 显式设 0.2, AutoHeist 设 1。**注意 `debug_mode` 下 `sleep()` 直接 `time.sleep` 跳过钩子。**
2. **SceneFlow `interrupt` + `safe_point()`** —— FishingTask(需先把任务重写成声明式状态机, `safe_point` 会抛 `SceneReplan`)。

改动: 删掉 4 处循环内显式调用, 改为 `SLEEP_CHECK_INTERVAL = 0.5` + `__init__` 里 `self.sleep_check_interval = ...` + `sleep_check()` 覆写(与 VolleyballTask 同构)。覆盖范围反而更大: 出价中间步骤、`_sell_collections`、`_wait_bid_screen` 的 post_action sleep 都被覆盖。`_recover_blocking_popup()` 兜底保留。
测试: 删掉 4 个循环集成用例, 改为 `sleep_check` 命中/no-op 2 条 + 兜底 3 条; 另在 `TestAutoBidAuctionFrames.TestAuctionRegionGeometry` 加一条"必须启用 sleep_check_interval"的接线断言(离线用例用的是 `object.__new__`, 拿不到 `__init__` 的赋值, 只有真实例能验)。结果: 95 + 20 tests OK。
姐妹任务 `AuctionHouseUpkeepTask(AutoBidAuctionTask)` 继承 `__init__` 与 `sleep_check`, 自动获得同一修复。

## 核查: 轮询循环里的 self.next_frame() 是否必需(实测结论)

ok-script 的帧缓存机制(源码位置: `ok/task/task.py` 的 `ocr`/`find_feature`, `ok/task/TaskExecutor.py` 的 `frame`/`next_frame`/`reset_scene`/`sleep`):
- `ocr()` / `find_feature()` 都是 `image = frame if frame is not None else self.executor.frame`;
- `executor.frame` 是懒抓帧属性: `if self._frame is None: self.next_frame()`, 否则直接返回缓存的 `self._frame`;
- 清空缓存(`_frame = None`)的入口: `sleep()`(任意时长, 连 `sleep(0)` 也清, 因为 `reset_scene` 在 early-return 之前)、`send_key` / `send_key_down` / `send_key_up`、`wait_condition`(即 `wait_until` / `wait_ocr`)、`next_frame()` 自身。

用 `TaskTestCase` 脚手架 + 真实截图实测(计数器包在 `executor.next_frame` 上):
- 循环A 显式 `next_frame()` + 2 次 ocr + `sleep` ×3 轮 → 抓帧 3 次
- 循环B **去掉** `next_frame()` + 2 次 ocr + `sleep` ×3 轮 → 抓帧 **也是 3 次**(每轮首个 ocr 懒抓帧)
- 循环C 去掉 `next_frame()` 且**不 sleep 不交互** ×3 轮 → 抓帧 **只有 1 次**(3 轮都在分析同一帧, 这才是 bug)
- 同一迭代内两次 ocr 共用同一帧 = True; `sleep` 之后 `_frame is None` = True

结论: `AutoBidAuctionTask` 的 4 处 `next_frame()`(每轮末尾都有 `sleep(POLL_INTERVAL)`)功能上冗余但**建议保留** —— 成本与懒抓帧完全相同, 且把"帧新鲜度"与 sleep 的副作用解耦, 防止将来循环改成不 sleep 时静默读到旧帧。仓库其它调用点同属此类; `frame = self.next_frame()`(BaseCombatTask:536 / BagelAITools:1147 / HeistTask:252)属于"要帧对象本身", 必须有。

## 复核: 拍卖任务的超时机制(实测数据)

- 结构: `_exec_auction_round` 一轮一个绝对 deadline(`time.monotonic() + ROUND_TIMEOUT=600`), 每次等待用 `_remaining_timeout(deadline, limit)` 钳制, 到期抛 `WaitFailedException("单轮拍卖超时")`; 嵌套阶段截止用 `min(deadline, now + 阶段上限)`。全文件 18 处 wait_* 都有 time_out, 无裸等。
- 实测单轮迭代开销(测试脚手架, 静态图): next_frame 26ms, 小区域 ocr 3-140ms, "1 抓帧 + 4 次状态 OCR" ≈ 49ms; 加 `sleep(0.5)` 后一轮 ≈ 0.55s。
- 由此: `MATCH_MAX_LOOPS=120` ≈ 66s **先于** `MATCH_TIMEOUT=120s` 到期(配置的 120s 实际够不着); `RESULT_MAX_LOOPS=180` ≈ 99s 晚于 `RESULT_TIMEOUT=90s`(计数上限形同虚设)。两套上限重叠且不一致。
- 其它发现: `_remaining_timeout` 三种预算(round/stage/result)共用同一条 "单轮拍卖超时" 消息 → 日志误导; `_remaining_timeout(deadline, 0.1)` 被当"检查截止"用 3 处; `_wait_bid_screen` 的 60 未提常量; `_run_post_round_actions` 用同一 round deadline, 附加流程超时会把已成功的拍卖轮记成失败; `do_run` 失败重试无上限 + `add_rounds_config()` 默认 0=无限(8 个任务共性), 界面永久不可读时按 600s/轮 无限重试(月卡事故即此形态)。
