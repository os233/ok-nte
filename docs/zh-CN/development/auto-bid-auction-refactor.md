# AutoBidAuctionTask 重构分析

## 目的与范围

本文分析 `AutoBidAuctionTask` 当前承担的职责、主要逻辑模块和依赖关系，并提出渐进式拆分方案。目标是降低单文件的维护成本，同时保持任务行为、用户配置和框架调用契约不变。

当前任务实现位于 `src/tasks/AutoBidAuctionTask.py`。任务由 `src/config.py` 按模块路径注册，因此该任务类及注册路径应继续保留。仓库中另有 `auction-layering.md` 历史提案，其行数和部分结构统计基于较早代码快照；本文以当前源码为准，不沿用旧估算。

## 当前职责

`AutoBidAuctionTask` 不只是拍卖出价循环，而是一个同时包含任务生命周期、界面状态机、价格策略、低保领取、藏品出售、掉线回场和 UI 配置的任务类。

任务继承 `NTEOneTimeTask` 和 `BaseNTETask`，复用框架提供的轮次管理、日志、睡眠钩子、OCR、截图区域和模拟点击能力。`run()` 确保框架连接已就绪；`do_run()` 管理轮次、配置校验、单轮异常和最终收尾。

当前实现已经有几个可用于模块协作的类型：

- `AuctionState` 表示单轮拍卖的可识别界面阶段。
- `AuctionBoxes` 集中传递拍卖 UI 区域。
- `PostRoundState` 在结算观测和轮末出售之间传递满仓观测等结果。

出售状态、低保日计数、上一轮出价等仍保存在任务实例字段中。拆分时需要明确这些字段的生命周期和唯一所有者。

## 主要逻辑模块

| 模块 | 当前职责 | 依赖与边界 |
|---|---|---|
| 任务入口与轮次编排 | 配置校验、构造区域、启动轮次、捕获单轮异常、处理仓库残留 | 依赖框架轮次 API；建议继续留在任务类 |
| UI 区域与界面识别 | 构造 `AuctionBoxes`、定义 OCR 正则、判断匹配/确认/出价/跳过/主界面/世界界面 | 依赖坐标与 OCR；区域定义可独立于识别行为 |
| 单轮拍卖状态机 | 匹配、确认、出价、结果阶段及阶段内重试；共享轮次 deadline | 强依赖任务状态、OCR 与输入；宜作为完整边界迁移，不要拆散状态转换 |
| 出价策略与价格输入 | 读取出价配置、解析估价、计算多轮价格、自动加价、指定回合价格、数字键盘输入及输入校验 | 可分为纯价格决策与 UI 读写两部分 |
| 结算后辅助流程 | 满仓观测、资产观测、低保领取、每日次数记录、表情包 | 低保阶段会影响出售品质选择，二者存在策略耦合 |
| 藏品出售 | 出售模式、间隔策略、仓库操作、品质筛选、出售验证、失败升级与清理 | 依赖满仓状态、低保阶段和任务配置；跨轮失败状态必须保留 |
| 掉线回场与弹窗恢复 | 世界界面探测、回到拍卖入口、恢复入口卡片、处理遮挡弹窗 | 依赖特定界面与输入，并共享阶段/轮次时限 |

## 依赖关系

整体依赖可以概括为：

```text
配置注册 (src/config.py)
        │
        ▼
AutoBidAuctionTask
  ├─ 框架能力: NTEOneTimeTask / BaseNTETask
  │    ├─ 轮次管理、日志、睡眠钩子
  │    └─ OCR、截图区域、普通输入
  ├─ 界面契约: AuctionBoxes + OCR 正则
  ├─ 单轮状态机: 匹配 → 确认 → 出价 → 结果
  ├─ 结算后处理: 满仓/资产观测、低保、表情
  ├─ 藏品出售: 模式决策 → 仓库交互 → 结果验证
  └─ 回场恢复: 世界界面 → 拍卖入口
```

`AutoBidAuctionTask` 是框架任务入口和能力之间的协调者。新模块应依赖明确的输入（例如 `AuctionBoxes`、deadline、策略结果），并通过任务对象访问框架 OCR/输入 API；不建议引入通用容器、全新服务层或运行时框架。

## 可拆分边界

### 1. 配置声明

任务配置默认值、控件类型、条件可见项和说明文本不需要游戏运行状态，可放入 `auction/options.py`。`CONF_*` 等曾在 `AutoBidAuctionTask` 上保留类级兼容别名以维持配置契约; 2026-09-28 起别名已收掉, 任务类与测试直接从 `auction.options` / `auction.layout` 导入常量, 出售 / 低保 / 回场的行为常量下放到各自子包模块。这是一次破坏性接口变更: 仓库外脚本若引用 `AutoBidAuctionTask.CONF_*` / `BOX_*` 等类级别名, 会直接 AttributeError, 需改为从 `auction.options` / `auction.layout` 导入, 任务类不再提供转发。

### 2. UI 区域定义

`AuctionBoxes` 和拍卖专属区域数据适合集中到 `auction/layout.py`。OCR 裁剪框是任务专属定义，不应为了复用而塞进通用场景位置抽象。区域数据搬迁后需核对每个字段映射和构造结果。

### 3. 价格决策与 UI 输入

估价倍率、加价模式、指定回合和价格列表可整理为价格决策逻辑：输入配置、轮次和观测值，输出目标价格。OCR 读数、键盘输入、输入结果校验仍需要任务视觉/操作 API，可由任务协调或作为独立适配方法保留。

先拆纯规则与界面副作用，避免在抽取时同时改变价格舍入、估价读取、重试条件或输入节奏。

### 4. 藏品出售

出售可以作为一个整体能力模块，涵盖模式判定、间隔策略、品质选择、仓库交互、出售验证和失败升级。必须一并保留以下语义：

- 满仓出售失败会影响后续轮是否跳过拍卖。
- 超时导致的“结果未知”不能等同于明确出售失败。
- 品质按钮是切换式点击，重复点击可能反选。
- 出售异常时要尽量关闭仓库，避免将出售模式和品质勾选状态带到下一轮。
- 连续满仓失败的升级策略、成功后的计数清零规则应保持不变。

### 5. 低保与结算观测

低保弹窗、领取次数读取、跨日重置和出售品质策略互相影响。建议先作为一个低保能力边界处理，明确由谁维护每日计数；待接口稳定后，再考虑将纯日计数或品质选择规则单独抽取。

### 6. 回场与弹窗恢复

大世界探测、回场流程和遮挡弹窗恢复可以集中处理，但它们涉及具体界面特征、输入序列和局部时限。建议在配置/价格/出售等边界稳定之后再拆。

## 推荐模块布局

```text
src/tasks/
├─ AutoBidAuctionTask.py       # 框架任务入口、轮次编排、单轮状态机
└─ auction/
   ├─ __init__.py
   ├─ options.py               # 默认配置、控件类型、配置说明
   ├─ layout.py                # AuctionBoxes 与拍卖 UI 区域
   ├─ price.py                 # 价格解析与纯策略计算
   ├─ sell.py                  # 藏品出售流程与失败升级
   ├─ welfare.py               # 低保领取、次数记录与日切
   └─ recovery.py              # 掉线回场与遮挡弹窗恢复
```

这是职责方向，不要求一次性建立所有文件。每个模块应有清晰的输入输出和状态读写说明。若拆成 mixin，mixin 不应增加隐式实例字段；新增状态应由任务类统一初始化，避免状态重置遗漏。

## 建议的实施顺序

1. **固定契约和状态清单。** 记录任务注册路径、任务名、配置键和值、被直接调用的方法/常量、任务字段及其生命周期。尤其标明每个字段由哪些方法读写、在哪些轮次边界重置。
2. **抽取低耦合声明。** 先迁移配置声明和区域定义，核对默认配置、面板可见性、说明文本和区域映射。兼容别名不保留: 任务类与测试直接从子包导入 (2026-09-28 起, 见「1. 配置声明」)。
3. **拆价格逻辑。** 先迁移纯解析/计算，再整理估价 OCR、键盘输入及校验。此阶段不调整价格策略行为。
4. **整体迁移出售流程。** 将出售策略和仓库操作作为一个边界，保持 deadline、异常传播、失败升级、收尾关闭和状态复位一致。
5. **整理低保与结算后处理。** 明确低保计数、日切和出售品质选择的依赖，再移动相关逻辑。
6. **最后迁移回场/恢复能力。** 检查每次等待和回场操作继续使用原有的有界预算。
7. **再评估编排简化。** 各能力接口稳定后，才考虑是否需要进一步调整单轮状态机；不要把“拆文件”和“改控制流”放在同一阶段。

建议每个阶段形成独立、可审查的变更。当前测试集中在 `tests/TestAutoBidAuctionTask.py`，覆盖配置、价格、出售、低保、回场和时序行为。搬迁应保持既有断言语义；新增或修改测试前先阅读 `tests/TESTING.md`。

## 潜在风险与控制点

| 风险 | 可能后果 | 控制方式 |
|---|---|---|
| deadline 漏传或被重置 | 长时间空等、阶段超时失效、出售预算意外延长 | 为每类预算标明所有者；迁移时逐个核对调用链 |
| UI 操作次序或重试变化 | 错误点击、品质筛选反选、仓库残留 | 搬迁阶段保持操作顺序和条件不变；重点检查异常收尾 |
| 异常捕获层级变化 | 已成功轮次被记为失败，或失败未触发恢复 | 保持 `TaskDisabledException`、`WaitFailedException` 与普通异常的既有处理边界 |
| 状态生命周期改变 | 跨轮误跳过、出售升级提前触发、低保状态过期 | 维护字段读写/重置表；只在明确轮次边界重置 |
| 配置和测试兼容性 | 老配置失效、任务发现失败、外部脚本访问报错 | 保留注册路径和配置键; 类级别兼容别名已移除, 标注为破坏性接口变更 (2026-09-28) |
| 调试热重载不覆盖子模块 | 编辑子模块后仍运行旧代码，调试结果失真 | 实际核查调试重载机制；必要时开发阶段重启任务/应用，不假定子包自动热重载 |
| 一次性大范围迁移 | 难以区分结构变更与行为回归 | 按模块分阶段迁移，每阶段做针对性回归验证 |

## 结论

建议将重构定位为按依赖方向搬迁职责，并保持行为不变。优先抽取配置、区域定义和价格规则；之后迁移出售、低保与结算后处理；回场恢复放在后续阶段。轮次状态机和任务生命周期继续留在 `AutoBidAuctionTask`，由它协调各能力模块。

当前阶段不建议重写单轮状态机，也不建议先引入通用上下文容器或依赖注入框架。最重要的风险控制点是 deadline 传递、跨轮状态所有权、出售失败后的仓库清理和既有配置兼容性。
